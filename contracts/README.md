# Public client contract

`http-v2.json` lists the current control API operations used by the Cellapp CLI, app-host data entry points, success shapes and error codes. It changes visitor key semantics: platform login is required, key redemption creates a user grant, and rotation does not revoke prior grants. `http-v1.json` records the earlier static-only contract. `local-state-v1.json` still describes `cellapp.json`; data table manifests are separate non-secret `cellapp.data.json` files and are never stored inside project association state.

If app creation commits but data provisioning fails, `POST /apps` returns `app_data_not_ready` with `details.appId`. The CLI keeps the initial key in a mode-0600 file beside its origin-specific credential until publication, writes the non-secret app association, and retries the same app. Owners can inspect `errorCode` in data status and call `POST /apps/{app}/data/reconcile`; a persistent failure remains unready and is logged on the server. Older orphaned apps can be linked with `cellapp link <app-id> --output <directory>` after checking ownership in `cellapp apps`.

The CLI keeps deployment credentials in a private file under `~/.config/cellapp/`, named by the first 24 hexadecimal characters of SHA-256 of the HTTPS control origin. The legacy directory is `~/.config/ohmyapp/`. The credential JSON contains `token`, `expiresIn` and `origin`; only the token is sent as a Bearer credential. Migration copies the old file with mode `0600` and retains the old file for recovery until explicit logout, which revokes and removes both copies. New and legacy project files with different origin or different application IDs are treated as a conflict.

Control origin precedence is `--origin`, `cellapp.json`, `CELLAPP_ORIGIN`, `ohmyapp.json`, `OHMYAPP_ORIGIN`, then the built-in default `https://console.cellapp.ai`. This keeps existing project associations and legacy configuration on their original service. The `ohmyapp` command alias and `OHMYAPP_ORIGIN` are transitional. The reset-key command now returns `accessKey`, and first deploy returns `accessKey` instead of `shareKey`; old project association and credential migration still work without adding secrets to project files.

Owner app responses include `namespace` (user slug), `slug` (application slug), `aliasUrl`, and the HTTPS `url`. New applications use `{slug}-{namespace}.<apps-domain>` as their public host while the immutable app ID remains the authorization and data identity. The control-origin alias redirects to the current public host. Prior ID and previously assigned slug hosts remain bound to the same application. Existing aliases that cannot fit a DNS label retain their ID host until edited in the console. `POST /apps` accepts optional `namespace` and `slug` only when creating an application; `cellapp.json` may store these non-secret choices. User slugs require at least three characters. Both slug types reject reserved platform names, and the combined host label cannot exceed 63 characters. The console can change either slug after creation.
